# RAG知识库模块开发SPEC（最终定稿版，可直接投喂AI编码）
## 一、项目整体概述
本模块为集团AI中台RAG知识库系统，提供**文档上传、结构化解析、智能分块、向量化入库、知识图谱构建、混合检索**全链路能力，扩展支持图片知识库、音视频知识库，实现文搜图、图搜图、文搜音视频召回推荐。

系统适配：前后端页面人工上传 + 外部API客户端批量上传双场景；适配ARQ异步流水线、支持多解析引擎切换、多策略分块、可选图片AI增强、可选知识图谱增强。

架构原则：**权限上层收敛、底层存储无权限判断；全局单例异步客户端；可配置化解析/分块/增强策略；完全私有化可部署**。

---

## 二、路由与资源隔离规范（强制）
1. 所有RAG模块接口统一前缀：`/api/rag`
2. 资源隔离规则：以**知识库ID(kb_id)**为核心维度做数据隔离
   - ES向量索引、Neo4j图谱、业务数据全部绑定 `kb_id` 前缀隔离
   - 底层存储（ES/Neo4j）**不做任何权限校验**，只根据传入的 kb_id 和其他 filter 参数查询
   - 所有数据权限、功能按钮权限全部由上层 RBAC + ACL 控制

---

## 三、权限体系设计（最终定稿，严格执行）
### 3.1 功能权限（RBAC）
仅控制RAG模块**菜单可见、页面准入、新建知识库**等全局功能入口，不再维护行级按钮权限。

### 3.2 数据权限（ACL+DataScope）
支持**用户、角色、部门、用户组**四主体资源授权，精准控制用户可访问的知识库ID列表。
**核心规则：**
1. 底层 ES / Neo4j / 数据库 **不实现任何ACL逻辑**
2. 后端接口根据当前用户权限，提前算出**可访问 kb_id 白名单**
3. 查询向量/图谱/文档时强制过滤白名单 kb_id，彻底杜绝越权
4. 页面可见 ≠ 资源可操作，完全依赖上层ACL资源授权

## 四、异步任务架构改造（ARQ流水线）
原有ARQ工作流流水线基础上，新增**双流水线隔离机制**。
### 4.1 启动参数改造
改造 `run_workers`、docker启动脚本、scripts启动脚本，新增启动参数：`-t [workflow/ragflow]`
- `workflow`：启动原有工作流任务队列
- `ragflow`：启动RAG文档解析、分块、向量化、图谱构建、多模态媒体处理队列

两套队列**完全隔离消费**，互不阻塞。

### 4.2 GPU适配规则（无需GPU开关）
1. Docling：纯CPU可运行，pip直接安装，无需独立部署
2. MinerU：私有化API部署模式，**通过HTTP接口调用**，本地worker不承载模型算力
3. 多模态Embedding、视频理解大模型：全部走私有化HTTP API，本地无模型依赖
结论：**ragflow worker 无需适配GPU参数**，全CPU运行即可，兼容未来任意服务器配置。

## 七、文档问答型知识库（kb_type=doc）设计
### 7.1 支持文件类型
1. **文档格式**（进解析引擎）：PDF、DOCX、PPT、EXCEL、MARKDOWN、HTML、JSON、TXT 等主流文档类型
   （`pdf/docx/doc/pptx/ppt/xlsx/xls/csv/md/markdown/html/htm/json/txt`）
2. **媒体格式**（不进解析引擎，由大模型先转写成文字）：
   - 图片：`jpg/jpeg/png/webp/bmp/gif`
   - 音频：`mp3/wav/m4a/aac/flac`
   - 视频：`mp4/mov/avi/mkv/webm`
> 媒体文件转写完成后与普通文档共用同一条流水线：分块 → 文本向量化 → 可进知识图谱 → 切片照常编辑/停用。一个知识库仍然只有一种向量空间，检索口径不变（音频/视频命中落在「文本」，图片命中落在「图片」并可展示原图）。

### 7.2 解析引擎三选一（创建知识库时配置）
1. **native原生解析（默认）**：使用pyPDF、python-docx、openpyxl等传统轻量解析库，无模型依赖，速度快
2. **docling增强解析**：pip直接依赖，轻量化版面分析、表格识别、双栏还原，CPU运行
3. **minerU增强解析**：私有化HTTP API部署，适配扫描件、图书、OFD公文、双栏教材高精度解析
> 也可由系统自动根据文档复杂度自动选择引擎，无需用户手动指定。
> 引擎的适用格式只有上面第 7.1-1 项：引擎从图片/音频/视频里抽不出正文，这类文件在解析阶段直接绕过引擎走转写分支（见 §7.1-2、§7.3），落库时 `parser_engine` 仍记用户在库里选的那个引擎，好让重跑能复用解析产物。

**各引擎真读得动的文档格式**（配置页要按这一份写清覆盖范围）：清单由 `/knowledge-bases/runtime-config` 的 `engineFormats` 下发，数据源就是解析层引擎类自己的 `formats` 声明——前端自己抄一份，改一次支持面就有一处不说实话。

| 引擎 | 文档格式 | 文档**内嵌**媒体能取到哪些字节 |
|---|---|---|
| native | `pdf/docx/pptx/xlsx/xls/csv/md/markdown/html/htm/json/txt` | 图片 + **音频 + 视频**（docx/pptx 的媒体部件、PDF 内嵌图片） |
| docling | 同 native（同样不含老版 Office） | **只有图片**，且取决于 docling 版本能否把图片导成内联字节；内嵌音频/视频取不到 |
| minerU | `pdf/docx/doc/pptx/ppt/md/html` 等（`.doc/.ppt` 能否吃取决于部署的 minerU 版本） | **只有图片**（服务回 `images` 才有字节）；内嵌音频/视频取不到 |

1. **老版 Office 的 `.doc/.ppt` 一律拒收**：python-docx / python-pptx 与 docling 都只认 Office Open XML 的 zip 包，读不动 OLE2 复合文档。拦截统一放在解析层基类（三引擎共用一份文案），报错必须带上「另存成什么」与「可以换哪个引擎」；native 与 docling 的 `formats` 声明里必须剔掉这两个后缀，否则页面上就会出现「清单说能吃、递过去就抛异常」的假承诺。
2. **内嵌音频/视频只有 native 取得到字节**。对另两个引擎来说，「开了音视频解析增强」不是「不给增强」而是「没有可增强的对象」——配置页的提示要照这句写，不许把开关写成被引擎禁用。
3. 一份「只嵌了媒体、没有正文」的 docx/pptx 走 docling 会导出空 markdown。解析层这时要先数一遍原文件包里的媒体件数再报错：确有媒体时报「docling 没导出媒体、请改用 native」，不许丢一句误导的「文档内容为空或格式无法识别」。

### 7.3 文档预处理与媒体模型可配置项
创建知识库时配置，全局生效；全部落在 `parse_config` 里（图片理解模型例外，它是库表列 `image_model_id`），不额外加数据库列：
1. 是否移除目录标题
2. 是否移除页眉页脚
3. **三个「解析增强」开关**：`image_understand` / `audio_understand` / `video_understand`，默认全关。页面上**常显、不限解析引擎**，语义与取值边界见 §7.4
4. **图片理解模型**（`image_model_id`，能力类型 `image_understand`）：**公用配置、常驻显示**——文档内嵌图片的解析增强与直接上传的图片文件都调这一枚模型；关掉开关**不清空**选择（这一栏还被另一条链路用着）
5. **音频解析模型**（`audio_model_id`，能力类型 `audio_to_text`）：上传音频文件**或**开启音频解析增强时必填——整条音频转写成正文，文档内嵌音频也送它
6. **视频解析模型**（`video_model_id`，能力类型 `video_understand`）：上传视频文件**或**开启视频解析增强时必填——整条视频描述成正文，文档内嵌视频也送它
7. **图片描述提示词**（`image_desc_prompt`）、**视频内容描述提示词**（`video_desc_prompt`）：留空使用内置默认提示词
> 缺对应模型的**媒体文件**解析**失败**（不静默跳过，文档格式不受影响），原因写进文档行的 `error_msg`，页面直接可读：例如「解析音频文件需要在知识库的解析配置里选择音频解析模型（音频转文字），当前未配置或该模型已停用」。
> 缺对应模型的**文档内嵌媒体**只降级不失败：正文仍带原位地址与占位词，另附一句解析告警说明增强没生效——内嵌媒体不是文档主体，为一句话把整篇判死不成立。
> 前端在提交前就拦「开关开着但模型没选」这一类组合：解析层只会塞一句降级警告，用户看到的仍是「已完成」，正文里却一个描述也没有。

### 7.4 解析增强开关（图片/音频/视频，默认全部关闭）
1. **开关不限解析引擎、页面上常显**：三个开关各管一种媒体，与选了哪个引擎无关（引擎能不能取到那种媒体的字节是 §7.2 的事，不该由开关去冒充引擎能力）。
2. **不论开关开闭都必须做**：把文档内嵌的媒体原件传对象存储，并把地址回填到正文里这一张图/这一段音视频原来的位置。这是硬需求，不是可选项——所以「关掉增强」绝不等于「忽略图片」。
3. 关闭：正文里只有原位地址与占位词（`[图片]`/`[音频]`/`[视频]`），不调任何大模型，一分钱不花。
4. 开启：在地址的**下面一行**追加模型生成的描述。占位词在有描述时被替换掉，`content_preview` 与切片正文同一条口径。
5. 描述进向量文本，因此开启后能按内容检索到这张图/这段音视频；未开启时向量里只有文件名与占位词。
6. 三种媒体送**不同的模型端点**（图片理解 / 音频转写 / 视频理解），协议各不相同，不是同一枚模型换个提示词。
7. 增强失败只降级不失败：没配模型、模型报错、地址取不到，一律写进解析告警并保留「地址 + 占位词」。
8. 直接上传的媒体文件（不是文档内嵌）也共用这些模型：出描述作为正文，原件已在存储不重复上传，切片仍保留媒体地址供预览。
> 保障图文顺序完全不变，结构化还原完整文档语义。

### 7.5 分块策略体系（全部前端可配置，统一单块上限20000字符）
| 分块模式 | 配置项 |
|---|---|
| 固定文本长度分块 | 单块最大字符数、是否重叠、重叠字符数 |
| 自定义分隔符分块 | 多分隔符列表、单块最大字符数 |
| 标题层级分块 | 按一/二/三级标题分块、超长自动合并截断 |
| 每页单独分块（PDF专属） | 一页一个chunk，超限自动拆分 |
| 语义分块（LangChain） | 基于句子语义相似度聚类分块，单块最大字符数 |
| LangChain特色分块拓展 | 集成主流高质量分块器作为兜底 |
| Excel专属分块 | 每一块强制附带原始表头，保证表格语义完整 |
| 正则表达式分块 | 用户自定义正则规则，精准匹配章节/条款切割 |

**通用增强配置（全部分块生效）**：
图表、表格、图片上下文补齐，可配置前后上下文文字数量，丰富孤立图表的语义。

### 7.6 知识图谱增强
1. 创建知识库可选择开启/关闭图谱构建
   - 开启：文档分块、向量化完成后，自动抽取实体、关系，入库Neo4j
   - 关闭：仅构建向量知识库，不生成图谱数据
2. 文档级后置构建：知识库/文档列表展示图谱构建状态，未构建的文档展示「构建知识图谱」按钮，支持单文档手动触发构建。

## 八、图片知识库（kb_type=image）设计
1. 支持文件格式：JPG、PNG、WEBP、BMP等主流图片格式
2. 处理流程：
   - 原始图片上传OSS获取URL
   - 调用多模态Embedding API，输入图片生成1024维图像向量
   - 写入ES：一条图片记录 = 一条图像向量 + OSS URL + 基础元数据
3. 检索能力：
   - 文搜图：文本query生成多模态向量，KNN召回相似图片
   - 图搜图：用户上传query图片生成向量，KNN召回相似图片
4. 不做图片自动描述，不支持知识图谱。

---

## 九、音视频知识库（kb_type=audio_video）设计
1. 支持文件格式：MP3、WAV、MP4、MOV、AVI等主流音视频格式
2. 处理流程（不抽关键帧、不做ASR字幕提取）：
   - 原始音视频上传OSS获取URL
   - 调用**视频/音视频理解大模型API**，一次性输出整条媒体的综合文本描述（`media_summary`）作为元数据存储
   - 调用**多模态Embedding API**，输入完整音视频文件，生成**单条全局多模态向量**（1024维）
   - 写入ES：一条音视频记录 = 1条全局向量 + media_summary文本 + OSS URL + 时长等元数据
3. 检索能力：
   - 文本query生成多模态向量，KNN召回语义匹配的整条音视频
   - 命中后返回音视频OSS URL + 大模型生成的summary摘要，前端可直接播放
4. 不做关键帧提取、不做ASR字幕识别、不做字幕分块、不支持知识图谱。

## 十、底层存储与向量规则
### 10.1 向量规则（固定不可改）
1. 全模态统一向量维度：**1024维**
2. 文本、图片、视频全局向量，共用同一个多模态Embedding向量空间，天然支持跨模态检索
3. 向量化模型在创建知识库选定后**永久锁定，不可修改**，防止向量语义空间错乱

### 10.2 ES索引设计
复用单索引 `rag_knowledge_chunk`，不按知识库类型拆索引，mapping字段：
```
org_id, kb_id, doc_id, chunk_id,
chunk_type: text/image/audio_video,
content: 文本chunk内容 / media_summary元数据,
embedding: 1024维dense_vector,
media_url: 媒体文件OSS地址,
is_deleted, create_time
```
> 所有检索前置filter：`kb_id IN (用户可访问kb白名单)`，先过滤再做KNN向量检索。

### 10.3 Neo4j设计
仅服务文档问答型知识库，节点/关系全部携带 `org_id, kb_id`，查询强制过滤白名单kb_id。

## 十二、部署与依赖结论（固定）
1. Docling：纯pip安装，CPU运行，无需独立私有化部署
2. MinerU：后续私有化HTTP API部署，项目通过HTTP调用，本地无模型依赖、无需GPU
3. 多模态Embedding、视频理解大模型：全部私有化HTTP API部署
4. ragflow队列：纯CPU架构，无GPU参数适配
5. OSS：统一存储所有原始文件、文档提取的图片、媒体文件，ES只存向量、元数据、OSS URL
