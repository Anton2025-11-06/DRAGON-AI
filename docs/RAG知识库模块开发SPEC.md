# RAG知识库模块开发SPEC（最终定稿版，可直接投喂AI编码）
## 一、项目整体概述
本模块为集团AI中台RAG知识库系统，提供**文档上传、结构化解析、智能分块、向量化入库、知识图谱构建、混合检索**全链路能力，扩展支持图片知识库、音视频知识库，实现文搜图、图搜图、文搜音视频召回推荐。

系统适配：前后端页面人工上传 + 外部API客户端批量上传双场景；适配ARQ异步流水线、支持多解析引擎切换、多策略分块、可选图片AI增强、可选知识图谱增强。

架构原则：**权限上层收敛、底层存储无权限判断；全局单例异步客户端；可配置化解析/分块/增强策略；完全私有化可部署**。

---

## 二、路由与资源隔离规范（强制）
1. 所有RAG模块接口统一前缀：`/api/rag`
2. 资源隔离规则：以**知识库ID(kb_id)**为核心维度做数据隔离
   - ES向量索引、Neo4j图谱、业务数据全部绑定 `kb_id` 前缀隔离
   - 底层存储（ES/Neo4j）**不做任何权限校验**，只根据传入的 kb_id 和其他 filter 参数查询
   - 所有数据权限、功能按钮权限全部由上层 RBAC + ACL 控制

---

## 三、权限体系设计（最终定稿，严格执行）
### 3.1 功能权限（RBAC）
仅控制RAG模块**菜单可见、页面准入、新建知识库**等全局功能入口，不再维护行级按钮权限。

### 3.2 数据权限（ACL+DataScope）
支持**用户、角色、部门、用户组**四主体资源授权，精准控制用户可访问的知识库ID列表。
**核心规则：**
1. 底层 ES / Neo4j / 数据库 **不实现任何ACL逻辑**
2. 后端接口根据当前用户权限，提前算出**可访问 kb_id 白名单**
3. 查询向量/图谱/文档时强制过滤白名单 kb_id，彻底杜绝越权
4. 页面可见 ≠ 资源可操作，完全依赖上层ACL资源授权

## 四、异步任务架构改造（ARQ流水线）
原有ARQ工作流流水线基础上，新增**双流水线隔离机制**。
### 4.1 启动参数改造
改造 `run_workers`、docker启动脚本、scripts启动脚本，新增启动参数：`-t [workflow/ragflow]`
- `workflow`：启动原有工作流任务队列
- `ragflow`：启动RAG文档解析、分块、向量化、图谱构建、多模态媒体处理队列

两套队列**完全隔离消费**，互不阻塞。

### 4.2 GPU适配规则（无需GPU开关）
1. native：纯CPU的轻量解析库（pypdf/python-docx/openpyxl），pip直接安装，无需独立部署
2. MinerU：私有化API部署模式，**通过HTTP接口调用**，本地worker不承载模型算力
3. 多模态Embedding、视频理解大模型：全部走私有化HTTP API，本地无模型依赖
结论：**ragflow worker 无需适配GPU参数**，全CPU运行即可，兼容未来任意服务器配置。

## 七、文档问答型知识库（kb_type=doc）设计
### 7.1 支持文件类型
1. **文档格式**（进解析引擎）：PDF、DOCX、PPT、EXCEL、MARKDOWN、HTML、JSON、TXT 等主流文档类型
   （`pdf/docx/doc/pptx/ppt/xlsx/xls/csv/md/markdown/html/htm/json/txt`）
2. **媒体格式**（不进解析引擎，由大模型先转写成文字）：
   - 图片：`jpg/jpeg/png/webp/bmp/gif`
   - 音频：`mp3/wav/m4a/aac/flac`
   - 视频：`mp4/mov/avi/mkv/webm`
> 媒体文件转写完成后与普通文档共用同一条流水线：分块 → 文本向量化 → 可进知识图谱 → 切片照常编辑/停用。一个知识库仍然只有一种向量空间，检索口径不变（音频/视频命中落在「文本」，图片命中落在「图片」并可展示原图）。

### 7.2 解析引擎（创建知识库时配置：两选一 + 自动）
1. **native原生解析（默认）**：使用pyPDF、python-docx、openpyxl等传统轻量解析库，无模型依赖，速度快
2. **minerU增强解析**：私有化HTTP API部署，适配扫描件、图书、OFD公文、双栏教材高精度解析
> 另有 **auto**：由系统按文档复杂度（页数/内嵌图片数/首页可抽字符数）自动选引擎，并在解析后回填实际使用的引擎，用户不必手动指定。
> **docling 已按需求 1 从前后端下线**：可选引擎只剩 `PARSE_ENGINES_ALL = [native, mineru, auto]`，解析层不再有它的引擎类、requirements 不再依赖它。存量库 `parse_config` 里存过的 `docling` 由 `PARSE_ENGINE_LEGACY` 在归一时映射给 native——不改历史数据，否则旧库会被当成「未知引擎」而悄悄变了行为。
> 引擎的适用格式只有上面第 7.1-1 项：引擎从图片/音频/视频里抽不出正文，这类文件在解析阶段直接绕过引擎走转写分支（见 §7.1-2、§7.3），落库时 `parser_engine` 仍记用户在库里选的那个引擎，好让重跑能复用解析产物。

**各引擎真读得动的文档格式**（配置页要按这一份写清覆盖范围）：清单由 `/knowledge-bases/runtime-config` 的 `engineFormats` 下发，数据源就是解析层引擎类自己的 `formats` 声明——前端自己抄一份，改一次支持面就有一处不说实话。

| 引擎 | 文档格式 | 文档**内嵌**媒体能取到哪些字节 |
|---|---|---|
| native | `pdf/docx/pptx/xlsx/xls/csv/md/markdown/html/htm/json/txt` | 图片 + **音频 + 视频**（docx/pptx 的媒体部件、PDF 内嵌图片） |
| minerU | `pdf/docx/doc/pptx/ppt/md/html` 等（`.doc/.ppt` 能否吃取决于部署的 minerU 版本） | **只有图片**（服务回 `images` 才有字节）；内嵌音频/视频取不到 |

1. **老版 Office 的 `.doc/.ppt` 一律拒收**：python-docx / python-pptx 只认 Office Open XML 的 zip 包，读不动 OLE2 复合文档。拦截统一放在解析层基类（各引擎共用一份文案），报错必须带上「另存成什么」与「可以换哪个引擎」；native 的 `formats` 声明里必须剔掉这两个后缀，否则页面上就会出现「清单说能吃、递过去就抛异常」的假承诺。
2. **内嵌音频/视频只有 native 取得到字节**。对 minerU 来说，「开了音视频解析增强」不是「不给增强」而是「没有可增强的对象」——配置页的提示要照这句写，不许把开关写成被引擎禁用。
3. 一份「只嵌了媒体、没有正文」的 docx/pptx 导出空 markdown 时，解析层要先数一遍原文件包里的媒体件数再报错：确有媒体时报「当前引擎没导出媒体、请改用 native」，不许丢一句误导的「文档内容为空或格式无法识别」。

### 7.3 文档预处理与媒体模型可配置项
创建知识库时配置，全局生效；全部落在 `parse_config` 里（图片理解模型例外，它是库表列 `image_model_id`），不额外加数据库列。
配置页按需求 6 排成**五行**：①解析引擎 / 单分块最大长度 / 重叠长度 / 图片表格上下文填充 ②分块策略 + 该策略的动态配置项（每个策略都带一句说明与适用场景） ③预处理开关（移除目录、移除页眉页脚、表格转md、保留分页标记，**每个开关都带 ? 说明**） ④模型位 ⑤条件显示的增强开关。**「检索配置」页已删除**（需求 5）——检索参数是在检索时动态设置的，不该在建库时定死。
1. 是否移除目录标题
2. 是否移除页眉页脚
3. **三个「解析增强」开关**：`image_understand` / `audio_understand` / `video_understand`，默认全关。页面上**按第四行有没有配对应模型条件显示**（配了图片理解或 OCR 才显示图片开关，配了音频转文字才显示音频开关，配了视频理解才显示视频开关），不限解析引擎；语义与取值边界见 §7.4
4. **图片理解模型**（`image_model_id`，能力类型 `image_understand`）：**公用配置、常驻显示**——文档内嵌图片的解析增强与直接上传的图片文件都调这一枚模型；关掉开关**不清空**选择（这一栏还被另一条链路用着）
5. **音频解析模型**（`audio_model_id`，能力类型 `audio_to_text`）：上传音频文件**或**开启音频解析增强时必填——整条音频转写成正文，文档内嵌音频也送它
6. **视频解析模型**（`video_model_id`，能力类型 `video_understand`）：上传视频文件**或**开启视频解析增强时必填——整条视频描述成正文，文档内嵌视频也送它
7. **描述提示词由后端内置**（需求 6-第五行「开关打开后，不需要配置提示词，后台写个提示词用就行了」）：页面上不再有图片/视频描述提示词两栏，`PARSE_OPTION_DEFAULTS` 里保留 `image_desc_prompt` / `video_desc_prompt` 键位只为存量 `parse_config` 透传，实际生效的是服务侧的内置提示词
8. **表格转 markdown**（`table_as_text`，默认开）与**保留分页标记**（`keep_page_break`，默认关）：前者关掉只是把表格退成「列名: 值」逐行文本——不丢数据，丢的是行列结构，而且向量文本里也一并丢掉；后者在每页前补一个「第 N 页」标题块，好让「按页分块」以外的策略也能按页切并保留页码定位
9. **多模态描述增强**（`media_desc_enhance`，需求 4）：只出现在图片型/音视频型知识库的解析配置里，语义见 §八/§九
> 缺对应模型的**媒体文件**解析**失败**（不静默跳过，文档格式不受影响），原因写进文档行的 `error_msg`，页面直接可读：例如「解析音频文件需要在知识库的解析配置里选择音频解析模型（音频转文字），当前未配置或该模型已停用」。
> 缺对应模型的**文档内嵌媒体**只降级不失败：正文仍带原位地址与占位词，另附一句解析告警说明增强没生效——内嵌媒体不是文档主体，为一句话把整篇判死不成立。
> 前端在提交前就拦「开关开着但模型没选」这一类组合：解析层只会塞一句降级警告，用户看到的仍是「已完成」，正文里却一个描述也没有。

### 7.4 解析增强开关（图片/音频/视频，默认全部关闭）
1. **开关不限解析引擎，但按「第四行有没有配对应模型」条件显示**：配了图片理解或 OCR 模型才显示图片开关，配了音频转文字才显示音频开关，配了视频理解才显示视频开关——没配模型就不给勾，否则勾了只会换来一句降级警告，页面上看不出没生效。开关本身与选了哪个引擎无关（引擎能不能取到那种媒体的字节是 §7.2 的事，不该由开关去冒充引擎能力）。
2. **不论开关开闭都必须做**：把文档内嵌的媒体原件传对象存储，并把地址回填到正文里这一张图/这一段音视频原来的位置。这是硬需求，不是可选项——所以「关掉增强」绝不等于「忽略图片」。
3. 关闭：正文里只有原位地址与占位词（`[图片]`/`[音频]`/`[视频]`），不调任何大模型，一分钱不花。
4. 开启：在地址的**下面一行**追加模型生成的描述。占位词在有描述时被替换掉，`content_preview` 与切片正文同一条口径。
5. 描述进向量文本，因此开启后能按内容检索到这张图/这段音视频；未开启时向量里只有文件名与占位词。
6. 三种媒体送**不同的模型端点**（图片理解 / 音频转写 / 视频理解），协议各不相同，不是同一枚模型换个提示词。
7. 增强失败只降级不失败：没配模型、模型报错、地址取不到，一律写进解析告警并保留「地址 + 占位词」。
8. 直接上传的媒体文件（不是文档内嵌）也共用这些模型：出描述作为正文，原件已在存储不重复上传，切片仍保留媒体地址供预览。
> 保障图文顺序完全不变，结构化还原完整文档语义。

### 7.5 分块策略体系（全部前端可配置，统一单块上限20000字符）
共七种策略（`CHUNK_STRATEGIES_ALL`），配置页第二行选定策略后动态展示它的配置项，**每个策略都带一句说明与适用场景**（前端 `STRATEGY_META`）：

| 分块模式 | 配置项 | 说明 / 适合的场景 |
|---|---|---|
| 固定长度分块 `fixed` | 单块最大字符数、重叠长度 | 兜底档：结构不明确的文档按长度切，靠重叠保证语义不断 |
| 自定义分隔符分块 `delimiter` | 多分隔符优先级列表、单块最大字符数、重叠长度 | 段落/句子边界规整的长文（txt/md）；原「LangChain 递归分块」已并给这一档，两者只差 overlap |
| 标题层级分块 `title` | 按一/二/三级标题切、超长自动合并截断 | 有清晰标题体系的制度、手册、教材 |
| 按页分块 `page`（PDF/PPT 专属） | 一页一个chunk，超限自动拆分 | 幻灯片、扫描件、分页报告这类「页」本身就是语义单元的材料 |
| 语义分块 `semantic` | 相邻句相似度阈值、单块最大字符数 | 没标题也没固定格式、话题会漂移的长文；代价是要额外付句向量调用 |
| Excel 表头分块 `excel`（xls/xlsx/csv 专属） | 是否强制附带原始表头 | 表格类：每块带上表头，否则「72.5」这种数值孤零零没有含义 |
| 正则分块 `regex` | 用户自定义正则 | 按「第X章/第X条」这类固定话术精准切割 |

> 专属策略只对相应后缀开放（`CHUNK_STRATEGY_EXCLUSIVE_EXT`），选不到就置灰；历史库里存过的 `recursive` 由 `CHUNK_STRATEGY_LEGACY` 归一到 `delimiter` 并回一句降级警告。
> **标题面包屑前缀写入向量文本**（`title_path`，默认开）：把「一级标题 / 二级标题」这条路只拼进送去向量化的那份文本，展示正文不受影响。它回答的是「这段在讲什么」之外多一路「这段出自哪一章」——孤立小节（只在三级标题下留了一句话那种）没有章节上下文时最容易召不回；代价是同一句话在不同章节下向量文本不同，去重不能只按正文。

**通用增强配置（全部分块生效）**：
图表、表格、图片上下文补齐（`context_augment`：开关 + 前后各取多少字符），可配置前后上下文文字数量，丰富孤立图表的语义。

### 7.6 知识图谱增强
1. 创建知识库可选择开启/关闭图谱构建
   - 开启：文档分块、向量化完成后，自动抽取实体、关系，入库Neo4j
   - 关闭：仅构建向量知识库，不生成图谱数据
2. 文档级后置构建：知识库/文档列表展示图谱构建状态，未构建的文档展示「构建知识图谱」按钮，支持单文档手动触发构建。
3. **图谱向量投影**（需求 9a）：图谱真身落在 Neo4j，同时在 ES 建一份可供向量召回的投影索引 `rag_kg_vector`（实体与关系两类文档），图构建完成后自动增量同步。
4. **图谱增强检索（需求 9，LightRAG 式轻量策略）**：开了 `with_graph` 后，召回从「关键词+向量的一路」变成**两路叠加**：一路是按权重融合的切片召回，另一路是图谱召回：
   - 把用户问题喂给对话模型，抽取问题里的**实体**与**关系**（`chat_json`；抽不出来就退化成用原句去做向量匹配）
   - 抽出的实体、关系**各自**去 `rag_kg_vector` 做 kNN（实体路查 `kind=entity`、关系路查 `kind=relation`），按 `graph_scale` 取前 N 条，余弦分低于 `KG_VECTOR_MATCH_MIN_SCORE` 的丢弃
   - 命中的实体按 `graph_depth`（1~3 跳）在 Neo4j 上沿关系逐跳扩子图，再回捞它们溯源的原文切片
   - 图谱回捞的切片并进主结果（`recall=GRAPH` 并标注命中实体），三元组另附一段资料递给大模型；**两路结果是叠加**，不是互相重排
   - 三段独立降级：抽取失败 / 向量投影未就绪 / 图谱无可命中数据，都只记一句警告并退回「只用切片那一路」，不让整个接口报错
5. 图谱检索的深度与规模上限写死在常量：`KG_RETRIEVE_MAX_DEPTH=3`（与子图逐跳上限一致）、`KG_RETRIEVE_MAX_SCALE=50`，默认 `depth=2 / scale=10`，页面越界按上限截。

---

## 八、图片知识库（kb_type=image）设计
1. 支持文件格式：JPG、PNG、WEBP、BMP等主流图片格式
2. 处理流程（一张图片 = 一条切片 = 一条向量，不进解析引擎也不分块）：
   - 原始图片上传OSS；**落库与落索引存的都是对象名**（预签名 URL 会过期，写进数据就是留下一批半年后打不开的媒体）
   - 调用多模态Embedding API，输入图片生成1024维图像向量
   - 写入ES：`content` = 文件名（开了「多模态描述增强」时是「文件名 + 模型描述」）+ 一条图像向量 + OSS URL + 基础元数据
3. 检索能力（需求 2：**文件名关键词 + 图片向量**双路，权重在检索页按百分比分配）：
   - 关键词一路：BM25 打在 `content` 上，默认命中的就是**文件名**（开了描述增强才连带命中图里的文字与内容描述）
   - 向量一路：文本 query 生成多模态向量 KNN 召回相似图片（文搜图）；用户上传 query 图片则图搜图
   - 两路按 `vector_weight` 加权融合后统一排序；只勾其中一路时该路占满 100%
4. **多模态描述增强**（`media_desc_enhance`，需求 4，默认关）：开启后必须配**图片理解模型或 OCR 模型**（二选一即可，两个都配时图片理解优先），由它给这张图生成综合描述拼在文件名后面；代价是每张图多一次模型调用，关掉则一分钱不花、只能按文件名命中。描述提示词由后端内置，页面不配置。
5. 不支持知识图谱（非 doc 型的支持列恒为 0），也不参与图谱增强检索。

---

## 九、音视频知识库（kb_type=audio_video）设计
1. 支持文件格式：MP3、WAV、MP4、MOV、AVI等主流音视频格式
2. 处理流程（不抽关键帧、不做字幕分块，一条媒体 = 一条切片 = 一条全局向量）：
   - 原始音视频上传OSS获取URL（同样只存对象名）
   - 调用**多模态Embedding API**，输入完整音视频文件，生成**单条全局多模态向量**（1024维）
   - 只有开了「多模态描述增强」才调模型出文字描述，与文件名拼成 `content`；未开时 `content` 只有文件名
   - 写入ES：一条音视频记录 = 1条全局向量 + content + OSS URL + 时长等元数据
3. 检索能力（需求 3：**文件名关键字 + 向量**双路，权重在检索页按百分比分配）：
   - 关键词一路：BM25 打在 `content` 上，默认命中的就是**文件名关键字**
   - 向量一路：文本query生成多模态向量，KNN 召回语义匹配的整条音视频
   - 命中后返回音视频 OSS URL + content，前端可直接播放
4. **多模态描述增强**（`media_desc_enhance`，需求 4，默认关）：开启后按需配**多模态视频理解模型**（给视频提画面描述）与**音频转文字模型**（把整条音频转成文本），两者共同组成这条媒体的综合描述。一条库不会同时装满音频和视频，所以校验按「至少配一个」卡，缺的那一路在解析时只记一句警告、不拖垮整篇。描述提示词由后端内置。
5. **原「基础信息里的媒体理解模型」已删除**（需求 4）：这一位（库表 `chat_model_id`）不再是音视频库的必填项，描述用的模型改从解析配置的视频理解/音频转文字两位取；`chat_model_id` 只剩 doc 型图谱抽取的存量回退。
6. 不做关键帧提取、不做字幕文件解析、不支持知识图谱。

## 十、底层存储与向量规则
### 10.1 向量规则（固定不可改）
1. 全模态统一向量维度：**1024维**
2. 文本、图片、视频全局向量，共用同一个多模态Embedding向量空间，天然支持跨模态检索
3. 向量化模型在创建知识库选定后**永久锁定，不可修改**，防止向量语义空间错乱

### 10.2 ES索引设计
**切片召回索引**复用单索引 `rag_knowledge_chunk`，不按知识库类型拆索引，mapping字段：
```
org_id, kb_id, doc_id, chunk_id,
chunk_type: text/image/audio_video,
content: 文本chunk内容 / 媒体库的文件名（+可选多模态描述）,
embedding: 1024维dense_vector,
media_url: 媒体文件OSS地址,
is_deleted, create_time
```
> 所有检索前置filter：`kb_id IN (用户可访问kb白名单)`，先过滤再做KNN向量检索。

**图谱向量索引** `rag_kg_vector`（需求 9a，`RAG_KG_INDEX`）：它是 Neo4j 的**向量投影**而不是图谱真身，可随时按库重建（`kg_vector.sync_kb_vectors` 增量算差集，文本没变的实体不再调向量模型）：
```
org_id, kb_id, kind: entity/relation,
name: 实体名 或 关系串,
etype: 实体类型 / 关系类型,
text: 送去向量化的文本（实体名 + 类型 + 摘要 / 关系描述）,
refs: 溯源键（回 Neo4j 反查 chunk 用）,
embedding: 1024维dense_vector, create_time
```
> `_id = {kb_id}_{kind}_{md5(name|text)[:16]}`，同一实体重建时按 `_id` 幂等覆盖；不给它建 MySQL 表。
> 与切片索引字段名分开（`KG_FIELD_*`），两套 mapping 互不干扰；**存量图谱不会自动补投影**，升级后需按库重跑一次向量同步（或重建图谱）才能用图谱增强检索。

### 10.3 Neo4j设计
仅服务文档问答型知识库，节点/关系全部携带 `org_id, kb_id`，查询强制过滤白名单kb_id。

## 十一、前后端功能清单
### 11.1 前端页面
1. 知识库创建/编辑/列表/删除，创建时三选一选择知识库类型（创建后不可改）
2. 上传文件弹窗：支持多文件批量上传，按知识库类型限制可上传文件格式（可上传后缀由 `/knowledge-bases/runtime-config` 下发）
3. 知识库配置面板：**只剩「基础信息 + 解析配置」两页**（需求 5：原「检索配置」页已删除，检索参数改在检索页动态设置）。解析配置按需求 6 排成五行（①引擎/单块长度/重叠长度/上下文填充 ②分块策略 + 动态项 + 策略说明 ③预处理开关且每个带 ? 说明 ④模型位（图片理解或 OCR 二选一、音频转文字、视频理解）⑤按第四行是否配了模型条件显示的增强开关）；基础信息页不再有音视频库的「媒体理解模型」（需求 4）
4. 文档列表：
   - 文档知识库：展示解析状态、图谱构建状态、手动构建图谱按钮
   - 图片知识库：展示图片网格预览
   - 音视频知识库：展示封面、时长、media_summary摘要预览
5. RAG检索页（需求 7/8/9：检索参数在这一页动态设置）：
   - 文档：文本输入，返回文本引用
   - 图片：支持文搜图、上传图搜图，结果以图片墙展示
   - 音视频：文本输入，返回音视频卡片，支持在线播放
   - **检索方式勾选 + 权重百分比条**（需求 7）：只勾「关键词」则该路 100%，只勾「向量」则向量 100%，两路都勾才用滑块分配（两者之和恒为 100%，页面用两段宽度可视化）
   - **重排模型下拉**（需求 8）：placeholder 为「不重排」，**没选就显式传 `rerank=false`**，绝不允许后端回落到库里存的开关（否则页面说没重排而实际重排了）
   - **知识图谱增强开关 + 深度(1~3)/规模(1~50)**、**对话模型下拉**（需求 9）：开图谱必须选对话模型（页面橙色警告 + 后端校验双卡）；未选模型只显示检索结果，选了模型则**左栏检索结果 + 右栏流式回答**，不做会话记忆，换了查询即清空
   - 命中卡片标注召回来源（`CHUNK`/`GRAPH`），图谱命中的还显示它来自哪个实体

### 11.2 后端接口
1. 页面人工上传接口、开放API客户端批量上传接口，`oss bucket的path_prefix=rag/ + key kb_id`，按kb_id做OSS对象前缀隔离
2. 异步任务进度查询、失败重试、取消任务
3. 知识库配置CRUD、文档管理接口
4. 手动触发文档知识图谱构建接口
5. 多模态检索接口：根据知识库类型自动切换召回逻辑
6. 检索入参（`RetrieveReq`）：`mode`（勾选组合换算成 KEYWORD/VECTOR/HYBRID）、`vector_weight`（0~1，只有两路都勾才传）、`rerank` + `rerank_model_id`、`with_graph` + `graph_depth` + `graph_scale`、`chat_model_id`
7. 流式问答接口 `POST /api/rag/retrieve/ask`（需求 9，SSE）：一帧 `meta`（左栏检索结果，CamelModel 输出的驼峰键）→ 多帧 `delta` → `done`（服务内手拼的帧沿用 snake 键 `took_ms`/`citations`）；失败只出一帧 `error`，不把异常抛成断流

## 十二、部署与依赖结论（固定）
1. native：纯 pip 安装的轻量解析库，CPU 运行，无需独立私有化部署（docling 已按需求 1 从 requirements 与前后端下线）
2. MinerU：后续私有化HTTP API部署，项目通过HTTP调用，本地无模型依赖、无需GPU
3. 多模态Embedding、视频理解大模型：全部私有化HTTP API部署
4. ragflow队列：纯CPU架构，无GPU参数适配
5. OSS：统一存储所有原始文件、文档提取的图片、媒体文件，ES只存向量、元数据、OSS URL
